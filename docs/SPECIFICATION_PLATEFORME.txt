PARTIE I — VISION & POSITIONNEMENT
================================================================================

1.1  QU'EST-CE QUE DEEPBLENDER ?
----------------------------------

DeepBlender est une plateforme SaaS qui transforme un prompt textuel en
production video/animation complete : scenario, storyboard, rendu 3D,
audio, musique, voix, sous-titres, et compositing final.

L'utilisateur decrit ce qu'il veut. Le systeme d'agents se charge de tout.

1.2  CAS D'UTILISATION CIBLES
-------------------------------

  Categorie            Exemple
  --------------------  ------------------------------------------------
  Films d'animation     Court-metrage 2D/3D, pilote de serie
  Publicites           Spot TV 30s, video produit, pub reseaux sociaux
  Contenu educatif     Tutoriel anime, explainer video
  Storytelling          Scene de manga animee, bande dessinee vivante
  Jeux video           Cinematiques, cutscenes, trails
  Contenu social       Clips TikTok/Reels animes, intros
  Prototypage rapide   Storyboard anime, animatic, previz

1.3  DIFFERENTIATEURS CLES

  a) Un seul prompt -> production complete (pas de tools separes)
  b) Agents IA qui collaborent comme une vraie equipe (scenariste,
     directeur, chef operateur, comedien, monteur...)
  c) Generation de musique originale (pas de copie, pas de royalties)
  d) Iteration en temps reel (l'utilisateur voit et modifie en cours)
  e) Observabilite totale (chaque decision est tracee et expliquee)
  f) Multi-moteur : Blender, Unreal Engine, Godot (extensible)
  g) Format VRM pour avatars cross-platform

1.4  PRINCIPES FONDATEURS

  P1. L'utilisateur est un createur, pas un technicien.
  P2. Chaque production est unique — jamais de templates generiques.
  P3. Transparence totale : l'utilisateur comprend chaque decision IA.
  P4. Iteratif par design : on peut toujours revenir en arriere.
  P5. Qualite professionnelle des le depart, pas un MVP.
  P6. Open-source d'abord pour les composants critiques.

2.3  MODULARITE DES MOTEURS DE RENDU

  Le systeme supporte multiple moteurs via une interface unifiee :

  Interface RenderingEngine
    +-- BlenderEngine     (blender -b -P script.py)
    +-- UnrealEngine      (UE5 -ExecutePythonScript + MRQ)
    +-- GodotEngine       (godot --headless --script)
    +-- AIVideoEngine     (CogVideoX / Wan2.1 pipeline)
    +-- HybridEngine      (Blender base + AI enhancement)

  Chaque moteur implemente :
    - generate_script(spec) -> str
    - execute(script, workdir) -> Result
    - inspect(workdir) -> SceneInfo
    - capabilities() -> Capabilities

  Le pipeline choisit le moteur selon :
    - La complexite de la scene
    - La qualite requise
    - Le budget GPU disponible
    - Les preferences utilisateur

3.1  HIERARCHIE DES AGENTS

  L'architecture suit un modele de collaboration inspire des vraies
  equipes de production cinematographique :

  ORCHESTRATEUR (PipelineRunner)
    Coordonne l'ensemble, gere les dependances, le parallelisme
    |
    +-- AGENTS DE PRE-PRODUCTION
    |     StoryAgent (Scenariste) -> StorySpec
    |     StoryboardAgent (Storyboard) -> StoryboardSpec
    |     DirectorAgent (Realisateur) -> SceneSpec
    |
    +-- AGENTS DE PRODUCTION
    |     CharacterDesigner* -> CharacterSpec[]
    |     EnvironmentArtist* -> Environment3D
    |     BlenderAgent (Chef Ope.) -> BlenderScript
    |     QAAgent (Directeur artistique) -> QAReport
    |     AnimatorAgent* -> AnimationClip[]
    |     Render (BlenderBridge) -> RenderOutput
    |
    +-- AGENTS DE POST-PRODUCTION
          AudioAgent (Musique & SFX) -> AudioPlan
          MusicComposer* -> MusicPlan
          SoundDesigner* -> SoundDesignPlan
          LocalizationAgent (Traduction & Voix) -> LanguagePackage[]
          CompositingAgent (Montage) -> CompositeSpec
          ReviewAgent* -> FinalReviewReport

  * = nouvel agent a implementer

3.2  NOUVEAUX AGENTS A IMPLEMENTER

  Agent              Role
  -----------------  ------------------------------------------------
  CharacterDesigner  Concevoir les personnages (look, poses, expressions)
                     Input: CharacterSpec -> Output: VRMModel
  AnimatorAgent      Animer les personnages (keyframes, contraintes,
                     lip sync, expressions faciales)
                     Input: ShotSpec + VRMModel -> AnimationClip
  EnvironmentArtist  Creer les environnements detailles
                     (modelisation, texture, eclairage HDRI)
                     Input: EnvironmentSpec -> Environment3D
  SoundDesigner      Conception sonore detaillee (foley, ambiances
                     spatiales, mixage)
                     Input: AudioPlan -> SoundDesignPlan
  MusicComposer      Composition musicale originale
                     (theme, leitmotiv, orchestrations)
                     Input: StorySpec -> MusicPlan
  ReviewAgent        Revue technique et artistique automatisee
                     (continuite, coherence, qualite)
                     Input: Production -> ReviewReport

3.3  COMMUNICATION ENTRE AGENTS

  Les agents communiquent via un systeme de messages cotes :

  MESSAGE BUS (EventBus)
    StoryAgent --publish(StorySpec)--> StoryboardAgent
    StoryboardAgent --publish(StoryboardSpec)--> DirectorAgent
    DirectorAgent --publish(SceneSpec)--> BlenderAgent
    BlenderAgent --publish(BlenderScript)--> QAAgent
    QAAgent --publish(QAReport)--> [RevisionRequest | Render]

  Chaque message est :
    - Type (schema Pydantic valide)
    - Trace (event_id, timestamp, agent_source)
    - Persiste (EventLog JSONL pour crash recovery)
    - Observable (SSE stream vers le frontend)

  Pattern de communication :

    # Publier un resultat
    event_bus.publish("story_completed", {
        "production_id": "abc-123",
        "agent": "StoryAgent",
        "output": story_spec.to_mapping(),
        "elapsed_s": 12.5,
        "model_used": "gemini-3.6-flash",
        "cost": 0.003
    })

    # S'abonner (pour orchestration)
    event_bus.subscribe("story_completed", handler=run_storyboard)

    # Revision ciblee
    event_bus.publish("revision_request", {
        "production_id": "abc-123",
        "target_agent": "BlenderAgent",
        "feedback": "La camera doit etre plus dynamique",
        "failed_steps": ["qa_visual"]
    })

3.4  MODELE D'ITERATION ITERATIVE

  L'utilisateur peut a tout moment :

  1. VOIR l'etat en temps reel (SSE stream)
  2. MODIFIER un patch structure (cible, pas de regeneration totale)
  3. REJETER et re-iterer un step specifique
  4. APPROUVER et avancer

  Exemple de flux de revision :

    Utilisateur : "La camera est trop statique"
      -> Patch(target="shot[2].camera.movement",
               old="static", new="travelling")
      -> DirectorAgent re-emet SceneSpec
        -> BlenderAgent regenere le script
          -> Render

    Utilisateur : "Refais la musique, trop triste"
      -> Patch(target="audio.music.mood",
               old="melancholic", new="epic")
      -> AudioAgent regenere l'AudioPlan

  Le systeme de patches EST DEJA IMPLEMENTE dans :
    - deepblender/domain/patch.py
    - deepblender/api/app.py (POST /productions/{id}/patches)
    - deepblender/production/runner.py (revision loop)

5.1  PIPELINE COMPLET (22 ETAPES)

  Le pipeline actuel (9 etapes) doit etre etendu a 22 :

  ETAPE  AGENT/PROCESSUS           SORTIE
  -----  -------------------------  --------------------------------
   1     StoryAgent                 StorySpec
   2     StoryboardAgent            StoryboardSpec
   3     [HITL] Approbation         Approved / Revision
   4     DirectorAgent              SceneSpec
   5     CharacterDesigner*         CharacterSpec[]
   6     EnvironmentArtist*         Environment3D
   7     BlenderAgent               BlenderScript
   8     QAAgent (script)           QAReport
   9     [Revision si needed]       Refined Script
  10     AnimatorAgent*             AnimationClip[]
  11     Render (BlenderBridge)     RenderOutput (video brute)
  12     [HITL] Preview             Approved / Revision
  13     QAAgent (render)           VisualQAReport
  14     MusicComposer*             MusicPlan
  15     SoundDesigner*             SoundDesignPlan
  16     AudioAgent                 AudioPlan (SFX, ambiances)
  17     LocalizationAgent          LanguagePackage[]
  18     TTS/Voix                   VoiceTracks[]
  19     CompositingAgent           CompositeSpec
  20     FFmpeg merge               Video + Audio + Subs
  21     ReviewAgent*               FinalReviewReport
  22     Export                     FinalOutput (mp4, mov, exr)

  * = nouvel agent a implementer

  PARALLELISME :
    Etapes 14-18 s'executent en parallèle (audio, musique, voix, localization).
    Etapes 5-6 peuvent tourner en parallele avec 7 si CharacterSpec et
    Environment3D sont prets.

5.2  CHECKPOINT & RESUME

  Chaque etape ecrit un checkpoint JSON :

  {
      "step": "blender",
      "status": "completed",
      "output_hash": "sha256:...",
      "output_path": "data/runs/{id}/blender_script.json",
      "elapsed_s": 45.2,
      "cost": 0.012,
      "model_used": "gemini-3.6-flash",
      "timestamp": "2026-08-24T23:00:00Z"
  }

  En cas de crash, le pipeline reprend au dernier checkpoint valide.
  DEJA IMPLEMENTE dans runner.py.

5.3  GESTION DES ERREURS & FALLBACK

  NIVEAU 1 : Retry immediat
    - Erreur reseau -> retry 1x avec backoff
    - Rate limit LLM -> pas de retry, fallback provider

  NIVEAU 2 : Self-repair (ReflexionStrategy)
    - Script invalide -> le LLM corrige avec le message d'erreur
    - QA echoue -> feedback injecte, regeneration ciblee

  NIVEAU 3 : Fallback deterministe
    - 2 echecs LLM -> script synthetise (qualite basique)
    - Moteur indisponible -> moteur alternatif

  NIVEAU 4 : Arret propre
    - Budget depasse -> arret avec etat sauvegarde
    - Erreur fatale -> arret, notification utilisateur

PARTIE VI — MOTEURS DE GENERATION
================================================================================

6.1  MOTEUR 3D : BLENDER (Principal)

  Etat actuel : Fonctionnel mais scripts LLM mal formats (filepath).
  Fix applique : render_dir injecte dans le contexte agent.

  Ce qui manque pour la production :

  a) ASSETS 3D :
     - Integrer Poly Haven API (HDRI, textures, modeles CC0)
     - Creer une bibliotheque locale de assets de base
     - Supporter l'import OBJ/FBX/glTF dans les scripts LLM
     - Ajouter un AssetManager plugin qui gere le cache

  b) PERSONNAGES :
     - Integrer des templates de personnages VRM
     - Supporter les armatures et le rigging automatique
     - Ajouter les blendshapes pour les expressions faciales
     - Supporter le lip sync via phoneme->blendshape

  c) ANIMATION :
     - Templates d'animations (marche, course, combat, gestes)
     - Retargeting d'animations sur nouveaux squelettes
     - Animation procedurale (IK, contraintes, drivers)
     - Motion blur et physics-driven animation

  d) QUALITE DE RENDU :
     - Denoising automatique
     - Volumetrics avancees (fog, god rays)
     - Reflections/refractions realistes
     - Post-process (bloom, DOF, tone mapping)

6.2  MOTEUR 3D : UNREAL ENGINE 5 (Haute Fidelite)

  Pour les scenes necessitant une qualite cinematographique :

  Integration UE5 :
    1. Script Python -> envoie commande via REST API au serveur UE5
    2. UE5 execute : level creation, material setup, lighting
    3. MRQ (Movie Render Queue) rend hors-screen
    4. Sortie : sequence d'images ou video H264/ProRes

  Avantages :
    - Nanite (geometrie haute densite sans polycount)
    - Lumen (eclairage global en temps reel)
    - MetaHuman (personnages realistes)
    - Chaos (physique avancee)

  Limites :
    - GPU requis (pas de CPU rendering)
    - Licence EULA (gratuit < $1M revenue)
    - Plus lent que Blender pour les scenes simples

  Quand utiliser UE5 :
    - Personnages realistes (MetaHuman)
    - Environnements photorealistes
    - Effets speciaux complexes (explosions, fluides)
    - Cinematiques de haute qualite

6.3  MOTEUR IA : COGVIDEX / WAN2.1 (Generation Directe)

  Pour les scenes ou la generation 3D est trop couteuse :

  Pipeline AI Video :
    Input : Prompt textuel + optional reference image
      -> CogVideoX (5B model, 16GB VRAM)
      -> ou Wan2.1 (14B model, 24GB+ VRAM)

  Sortie : Sequence video 4-8 secondes

  Usage :
    - Brouillons rapides (avant rendu 3D complet)
    - Effets speciaux (explosions, meteo, particules)
    - Transitions et interludes
    - Contenu social (clips courts)

  Integration :
    - GPU worker dedie (CUDA/ROCm)
    - API REST interne : POST /gpu/render-ai
    - Cache des generations (seed + prompt -> video)

6.4  HYBRIDE : BLENDER + AI

  Le mode le plus puissant :

  1. Blender cree la scene de base (geometrie, camera, lighting)
  2. AI genere les textures procedurales (Stable Diffusion)
  3. AI enrichit les details (fog, particles, reflections)
  4. AI post-traite le rendu (upscaling, style transfer)
  5. FFmpeg compositing final

  Ce workflow combine la precision de Blender avec la creativite de l'IA.

PARTIE X — SECURITE & CONFORMITE
================================================================================

10.1  AUTHENTIFICATION & AUTORISATION

  - JWT HS256 (access tokens, 1h TTL)
  - Refresh tokens (7 jours, rotation, revocation)
  - RBAC : owner / admin / editor / viewer
  - Multi-tenant : isolation par organization
  - Rate limiting : 60 req/min par IP

10.2  SECURITE DES SCRIPTS

  - AST validation (CodePolicy) : fail-closed
  - Imports autorises : bpy, math, mathutils, random, json
  - Builtins interdits : exec, eval, compile, open, input
  - Timeout subprocess : 300s (configurable)
  - Pas d'acces reseau depuis les scripts Blender

10.3  PROTECTION DES DONNEES

  - Chiffrement au repos (PostgreSQL TDE)
  - Chiffrement en transit (TLS 1.3)
  - Secrets dans Vault (pas en .env en prod)
  - Audit log (qui a fait quoi, quand)
  - RGPD : droit a l'effacement, export de donnees

10.4  CONFORMITE LICENCES

  - Assets CC0 (Poly Haven, Kenney) : pas de restrictions
  - MusicGen : CC BY-NC 4.0 -> pas commercialisable directement
  - Bark/Tortoise : MIT/Apache -> OK pour usage commercial
  - Blender : GPL -> OK (execute en subprocess, pas de linking)
  - UE5 : EULA gratuit (< $1M revenue)
  - CogVideoX/Wan2.1 : Apache 2.0 -> OK
